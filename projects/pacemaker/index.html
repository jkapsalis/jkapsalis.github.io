Introduction — What and why

Corosync keeps the cluster nodes in contact and decides who is a member. Pacemaker runs on top of it and decides where each service runs, moving it when a node fails. pcs is the command-line tool that configures both.

Project objective

Build a two-node cluster where a website stays reachable on one IP address even when a node goes down:

  • A floating IP that always lives on the active node
  • nginx started and stopped by Pacemaker, not by systemd
  • Automatic failover to node2 when node1 stops
0

Name resolution

0a — /etc/hosts Both nodes

Each VirtualBox VM has two adapters: NAT (enp0s3, always 10.0.2.15) and host-only (enp0s8, 192.168.56.x). The cluster must only use the host-only addresses:

/etc/hosts
192.168.56.107 node1
192.168.56.117 node2
⚠
Never map a node name to 10.0.2.15. Every VM has that same NAT address, so Corosync on each node ends up talking to itself. See problem 2 below.
1

Install the cluster stack

1a — Packages, pcsd and firewall Both nodes
dnf install -y pacemaker corosync pcs fence-agents-all resource-agents

# pcsd is the daemon pcs uses to talk to the other node
systemctl enable --now pcsd

# The cluster admin user exists but has no password. Use the SAME one on both nodes
passwd hacluster

# Open the Corosync, pcsd and Pacemaker ports
firewall-cmd --add-service=high-availability --permanent
firewall-cmd --reload
2

Create the cluster

2a — Authenticate and set up node1
pcs host auth node1 node2 -u hacluster
node1: Authorized
node2: Authorized

pcs cluster setup my_cluster node1 node2
Sending 'corosync authkey', 'pacemaker authkey' to 'node1', 'node2'
Sending 'corosync.conf' to 'node1', 'node2'
Cluster has been successfully set up.

pcs cluster start --all
pcs cluster enable --all   # start the cluster on boot
2b — Final corosync.conf Both nodes

pcs writes ring0_addr: node1 by default. I changed it to the host-only IPs so Corosync can never pick the NAT address:

totem {
    cluster_name: my_cluster
    transport: knet
    crypto_cipher: aes256
    crypto_hash: sha256
}

nodelist {
    node { ring0_addr: 192.168.56.107  name: node1  nodeid: 1 }
    node { ring0_addr: 192.168.56.117  name: node2  nodeid: 2 }
}

quorum {
    provider: corosync_votequorum
    two_node: 1     # a 2-node cluster keeps quorum with one node left
}
# Copy it to node2, then restart the cluster
scp /etc/corosync/corosync.conf node2:/etc/corosync/corosync.conf
pcs cluster stop --all && pcs cluster start --all
2c — Lab properties node1
pcs property set stonith-enabled=false
pcs property set no-quorum-policy=ignore
⚠
Lab only. STONITH (fencing) powers off a node that stops responding, so two nodes never run the same service at once. Without a fence device Pacemaker refuses to start resources, so this lab turns it off. A production cluster needs fencing.
3

Prepare nginx

3a — Install, but let Pacemaker run it Both nodes
dnf install -y nginx

# A page that shows which node answered
echo "<h1>Served from $(hostname)</h1>" > /usr/share/nginx/html/index.html

# Pacemaker starts nginx, so systemd must not
systemctl disable --now nginx

firewall-cmd --add-service=http --permanent
firewall-cmd --reload

Listen on all addresses so nginx answers on the floating IP, and expose a status page for local checks:

/etc/nginx/conf.d/status.conf
server {
    listen 0.0.0.0:80;
    server_name localhost;

    location /nginx-status {
        stub_status on;
        allow 127.0.0.1;
        deny all;
    }

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }
}
nginx -t
nginx: configuration file /etc/nginx/nginx.conf test is successful
4

Create the cluster resources

4a — Floating IP + web server as one group node1
# The floating IP
pcs resource create VIP ocf:heartbeat:IPaddr2 \
    ip=192.168.56.200 cidr_netmask=24 \
    op monitor interval=10s

# nginx, driven through its systemd unit
pcs resource create WebServer systemd:nginx \
    op monitor interval=20s \
    op start timeout=40s \
    op stop timeout=60s

# A group starts in order (VIP, then nginx) and always stays on one node
pcs resource group add WebGroup VIP WebServer

# Prefer node1 when both nodes are healthy
pcs constraint location WebGroup prefers node1=50
pcs status
Node List:
  * Online: [ node1 node2 ]

Full List of Resources:
  * Resource Group: WebGroup:
    * VIP       (ocf:heartbeat:IPaddr2):   Started node1
    * WebServer (systemd:nginx):           Started node1
5

Test failover

5a — Stop the active node
curl http://192.168.56.200
<h1>Served from node1</h1>

# Take node1 out of the cluster
pcs cluster stop node1

# From node2 or the host: the group moves and the same IP keeps answering
pcs status             # expected: VIP and WebServer Started node2
curl http://192.168.56.200   # expected: Served from node2

# Bring node1 back
pcs cluster start node1
ℹ
When node1 came back, the group moved back to node1 because of prefers node1=50. To keep it on node2 and avoid a second move, make resources "sticky" with a score higher than the preference: pcs resource defaults update resource-stickiness=100.
!

Problems I hit and how I fixed them

1 — pcs host auth: "Username and/or password is incorrect"

Cause: the hacluster user has no password after install.

# On BOTH nodes, with the same password
passwd hacluster
pcs host auth node1 node2 -u hacluster
2 — node2 OFFLINE, "partition WITHOUT quorum"

Cause: /etc/hosts also mapped node names to the NAT address 10.0.2.15, which every VM shares. Corosync resolved the names to the wrong network.

# What does the name really resolve to?
getent hosts node1 node2

# Is heartbeat traffic arriving on the host-only adapter?
tcpdump -i enp0s8 port 5405 -n

Fix: remove the 10.0.2.15 lines from /etc/hosts and set ring0_addr to the host-only IPs (step 2b).

3 — "nsscrypto: Digest does not match"
[KNET  ] nsscrypto: Digest does not match. Check crypto key and configuration.
[KNET  ] rx: Unable to decrypt packet from 192.168.56.117:5405 (size 80)!

Cause: the two nodes had different /etc/corosync/authkey files, so they could not decrypt each other's traffic.

# Compare on both nodes; the hashes must match
md5sum /etc/corosync/authkey

# Copy node1's key to node2, then restart both services
scp /etc/corosync/authkey root@192.168.56.117:/etc/corosync/authkey
systemctl restart corosync pacemaker
Online: [ node1 node2 ]   — partition with quorum
4 — WebServer "not installed" with ocf:heartbeat:nginx
* WebServer start on node1 returned 'not installed'
* WebServer start on node2 returned 'not installed'

The ocf:heartbeat:nginx agent kept failing. It still failed after I removed Apache (httpd) and pointed it at /usr/sbin/nginx. I didn't find the root cause.

Fix: let Pacemaker drive nginx's own systemd unit instead:

pcs resource delete WebServer
pcs resource create WebServer systemd:nginx op monitor interval=20s
pcs resource group add WebGroup WebServer
pcs resource cleanup
* WebServer (systemd:nginx): Started node1
5 — "invalid cluster property option 'default-resource-stickiness'"

Cause: stickiness is a resource default, not a cluster property, in current pcs versions.

pcs resource defaults update resource-stickiness=100
