Introduction — One script does the work

Internal services in a development environment still need TLS certificates, and a public CA will not issue them for internal hostnames. HashiCorp Vault's PKI secrets engine can act as a private certificate authority, but setting it up by hand takes a container, a token, a dozen API calls and several OpenSSL commands.

Vault-PKI-Interface-Manager.ps1 does all of that for you. Every step on this page is a function inside the script. You never type a Vault API call yourself:

  • On start-up it checks tools, starts Vault, gets the token and builds the CA
  • Then it opens a menu for the whole certificate lifecycle
  • Issue, list, read, revoke, export to PFX, view the CRL, tidy
  • Trust the root CA on Windows with one key press

What the script does on start-up

2a — Seven automatic steps Initialize-Application

Each step is skipped when it is already done, so running the script again is safe.

#FunctionWhat it does
1Test-RequirementsChecks that docker and openssl are installed
2Get-VaultCaConfigLoads vault-ca.config.json. On first run it asks for each setting and saves them
3Initialize-WorkingDirectoryCreates the folder where keys, CSRs and certificates are stored
4Initialize-VaultAddressSets VAULT_ADDR for the session
5Start-VaultReuses a running vault container, starts a stopped one, or creates a new one in dev mode. Waits until the API answers
6Initialize-VaultTokenReads the root token from docker logs, sets VAULT_TOKEN and validates it
7Initialize-PkiEnables pki/, publishes CA/CRL/OCSP URLs, generates the root CA, saves root-ca.crt and creates the signing role

When all seven pass, the script reports:

============================================================
       VAULT CA INITIALIZATION COMPLETED
============================================================
[OK]   Vault is ready.
[OK]   VAULT_ADDR is configured.
[OK]   VAULT_TOKEN is configured.
[OK]   PKI engine is ready.
[OK]   Root CA is ready.
[OK]   Signing role is ready.
2b — First-run settings vault-ca.config.json

Press Enter at each prompt to accept the default. The answers are saved, so you are only asked once:

{
  "WorkingDirectory": ".\\vault-ca-data",
  "PkiPath": "pki",
  "RoleName": "dev-role",
  "RootCACommonName": "example.com",
  "RootCAIssuerName": "root-ca",
  "RootCATtl": "87600h",      // root CA: 10 years
  "RoleDomain": "apps.dev.example.com",
  "RoleMaxTtl": "720h"        // leaf certificates: 30 days
}
💡
The role only signs names inside RoleDomain and its subdomains, for example api.apps.dev.example.com.

KeyFunctionWhat happens
1New-CsrOpenSSL creates an RSA 2048 key and a CSR for the name you enter, plus optional extra SANs
2Sign-CsrSends the CSR to Vault and saves <name>.crt and <name>-chain.crt
3Get-CertificateListLists every issued certificate by serial number
4Read-CertificateShows one certificate's details
5Revoke-CertificateRevokes a serial number after you confirm
6Show-CrlPrints the certificate revocation list
PExport-PfxBundles certificate, key and optional chain into a password-protected .pfx
7Invoke-TidyRemoves expired and revoked entries from Vault
TInstall-RootCaTrustAdds root-ca.crt to the Windows Trusted Root store
SStop-VaultStops the container after you confirm

Keys 8, 9, L and C show Vault's status, open the web UI, print the container logs and print the current settings.

Under the hood

The Vault API calls the script makes for you

This is only for understanding. The script makes these calls itself:

# Initialize-Pki: enable the engine and create the CA
POST /v1/sys/mounts/pki             {"type":"pki"}
POST /v1/pki/config/urls            {issuing_certificates, crl_distribution_points, ocsp_servers}
POST /v1/pki/root/generate/internal {"common_name":"example.com","issuer_name":"root-ca","ttl":"87600h"}
POST /v1/pki/roles/dev-role         {"allowed_domains":"apps.dev.example.com","allow_subdomains":true,"max_ttl":"720h"}

# Menu actions
POST /v1/pki/sign/dev-role          {"csr":"...","format":"pem"}     # [2]
GET  /v1/pki/certs?list=true                                          # [3]
GET  /v1/pki/cert/<serial>                                            # [4]
POST /v1/pki/revoke                 {"serial_number":"..."}             # [5]
GET  /v1/pki/cert/crl                                                 # [6]
POST /v1/pki/tidy                   {"tidy_cert_store":true,...}        # [7]

Every call carries the X-Vault-Token header that the script set in step 6.

Quick troubleshooting

Common issues & fixes

"The following required tools are missing":

# Install the listed tool, make sure it is on PATH, then run the script again
docker --version
openssl version

"common name ... not allowed by this role":

# The name must be inside RoleDomain. Check the settings with menu key [C],
# or delete vault-ca.config.json to answer the first-run prompts again.

Browser says the certificate is not trusted:

# The root CA is not trusted yet. Use menu key [T] from an admin PowerShell.
