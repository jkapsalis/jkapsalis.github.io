Introduction — What and why

Internal services in a development environment still need TLS certificates, but a public CA will not issue certificates for internal hostnames. A private certificate authority solves this, and HashiCorp Vault's PKI secrets engine provides one with an API: it signs certificates, keeps track of what it issued, revokes them and publishes a CRL.

Project objective

Wrap the whole certificate lifecycle in one PowerShell script, so a developer can:

  • Start a local Vault and configure the PKI engine automatically
  • Generate a private key and CSR, then sign it with the local CA
  • List, read and revoke certificates, and view the CRL
  • Export a .pfx bundle and trust the root CA on Windows

1

Start Vault in dev mode

1a — Run the container Docker

The script checks whether a vault container is running, stopped or missing, and only creates it when needed:

docker run -d \
  -e "VAULT_DEV_LISTEN_ADDRESS=0.0.0.0:8200" \
  -p 8200:8200 \
  --name vault \
  hashicorp/vault:latest \
  server -dev
⚠
Dev mode starts Vault already unsealed, keeps its data in memory and prints a root token to the logs. It is meant for a lab only. A real CA needs persistent storage, sealing and scoped tokens.
1b — Get the root token Docker

The script reads the token from the container logs and validates it with auth/token/lookup-self. By hand:

docker logs vault | grep "Root Token"
Root Token: hvs.XXXXXXXXXXXXXXXXXXXXXXXX

export VAULT_ADDR="http://localhost:8200"
export VAULT_TOKEN="hvs.XXXXXXXXXXXXXXXXXXXXXXXX"
ℹ
Never commit a token to git, even a dev one. Read it from the logs or an environment variable each time.
2

Configure the PKI engine

2a — Enable PKI and create the root CA Vault API

These are the API calls the script makes. Each step is skipped if it was already done.

# 1. Mount the PKI secrets engine at pki/
curl -H "X-Vault-Token: $VAULT_TOKEN" -X POST \
  -d '{"type":"pki"}' \
  $VAULT_ADDR/v1/sys/mounts/pki

# 2. Publish where clients find the CA, CRL and OCSP endpoints
curl -H "X-Vault-Token: $VAULT_TOKEN" -X POST \
  -d '{"issuing_certificates":["http://localhost:8200/v1/pki/ca"],
       "crl_distribution_points":["http://localhost:8200/v1/pki/crl"],
       "ocsp_servers":["http://localhost:8200/v1/pki/ocsp"]}' \
  $VAULT_ADDR/v1/pki/config/urls

# 3. Generate the root CA (private key never leaves Vault)
curl -H "X-Vault-Token: $VAULT_TOKEN" -X POST \
  -d '{"common_name":"example.com","issuer_name":"root-ca","ttl":"87600h"}' \
  $VAULT_ADDR/v1/pki/root/generate/internal
2b — Create a signing role Vault API

A role limits what the CA will sign: which domains and how long certificates live.

curl -H "X-Vault-Token: $VAULT_TOKEN" -X POST \
  -d '{"allowed_domains":"apps.dev.example.com","allow_subdomains":true,"max_ttl":"720h"}' \
  $VAULT_ADDR/v1/pki/roles/dev-role
SettingValueMeaning
Root CA TTL87600h10 years
Role max TTL720h30 days per leaf certificate
allow_subdomainstrueapi.apps.dev.example.com is allowed
3

Issue a certificate

3a — Private key + CSR OpenSSL

The key is generated locally, so Vault only ever sees the public CSR:

openssl req -new -newkey rsa:2048 -nodes \
  -keyout api.key -out api.csr \
  -subj "/C=GR/O=MyOrg/OU=Engineering/CN=api.apps.dev.example.com" \
  -addext "subjectAltName=DNS:api.apps.dev.example.com"
3b — Sign the CSR Vault API
jq -n --rawfile csr api.csr '{csr: $csr, format: "pem"}' \
| curl -s -H "X-Vault-Token: $VAULT_TOKEN" -X POST -d @- \
  $VAULT_ADDR/v1/pki/sign/dev-role \
| jq -r '.data.certificate' > api.crt

The script saves the certificate as <name>.crt and the CA chain as <name>-chain.crt next to the CSR.

✓
Check the result with openssl x509 -in api.crt -noout -subject -issuer -dates. The issuer should be CN=example.com.
4

Manage the lifecycle

4a — List, revoke, CRL, tidy Vault API
# List serial numbers of issued certificates
curl -H "X-Vault-Token: $VAULT_TOKEN" "$VAULT_ADDR/v1/pki/certs?list=true"

# Revoke one
curl -H "X-Vault-Token: $VAULT_TOKEN" -X POST \
  -d '{"serial_number":"<serial>"}' \
  $VAULT_ADDR/v1/pki/revoke

# Read the certificate revocation list
curl $VAULT_ADDR/v1/pki/cert/crl

# Clean up expired and revoked entries
curl -H "X-Vault-Token: $VAULT_TOKEN" -X POST \
  -d '{"tidy_cert_store":true,"tidy_revoked_certs":true,"tidy_expired_issuers":true}' \
  $VAULT_ADDR/v1/pki/tidy

Quick troubleshooting

Common issues & fixes

403 permission denied from the API:

# VAULT_TOKEN is empty or from an old container. Read it again:
docker logs vault | grep "Root Token"

"common name ... not allowed by this role":

# The CN must be inside allowed_domains. Check the role:
curl -H "X-Vault-Token: $VAULT_TOKEN" $VAULT_ADDR/v1/pki/roles/dev-role

Browser says the certificate is not trusted:

# The root CA is not in the trust store yet. Use menu option [T], or:
certutil -addstore -f Root root-ca.crt
